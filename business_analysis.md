# Бизнес-анализ проекта: Система обнаружения аномалий в транзакционной активности интернет-магазина

## 1. Бизнес-анализ (Business Understanding)

### 1.1. Организационная структура и стейкхолдеры
*   **Заказчик:** Средний или крупный интернет-магазин (e-commerce), который ежедневно обрабатывает тысячи транзакций.
    *   *В рамках учебного проекта заказчиком выступает сам студент, который моделирует ситуацию для реального e-commerce.*
*   **Стейкхолдеры и их интересы:**
    *   **Операционные менеджеры** — хотят быстрых алертов (в течение часа), чтобы реагировать на инциденты.
    *   **Аналитики** — хотят меньше ложных срабатываний, чтобы не тратить время на проверку «пустых» аномалий.
    *   **Технические специалисты** — хотят стабильности API и отсутствия нагрузки на инфраструктуру.
    *   **Финансовый директор** — хочет снижения потерь выручки на 5% за счет раннего обнаружения.
*   **Контакты и рабочие чаты:** В реальном проекте создаются чаты в Slack/Telegram. В учебном проекте коммуникация ведется через GitHub (Issues, Pull Requests) и документацию.

### 1.2. Бизнес-цель проекта
*   **Главная цель:** Сократить время обнаружения аномалий в транзакционной активности с **3 дней до 24 часов**.
*   **Существующие решения:**
    *   **BI-дашборды** (Tableau, Power BI, Superset) — аналитики визуально оценивают графики.
    *   **Простые правила в Grafana/Prometheus** — например, «если выручка упала на 30% — алерт».
    *   **Скрипты на Python** — аналитики пишут ad-hoc скрипты для проверки гипотез.
*   **Чем текущее решение не устраивает:**
    *   **Скорость:** Визуальный анализ занимает часы, а иногда и дни.
    *   **Человеческий фактор:** Аналитик может пропустить аномалию.
    *   **Ложные срабатывания:** Простые правила не учитывают контекст (например, крупные оптовые закупки).

## 1.1. Текущая ситуация (Assessing current solution)

*   Аномалии в исторических данных можно использовать для валидации модели (мы считаем, что резкие скачки выручки — это аномалии).

*   Модель будет работать на исторических данных, а не в реальном времени (в учебном проекте).
*   Бюджет проекта — 0 рублей (используем только open-source инструменты).

## 1.2. Решаемые задачи с точки зрения аналитики (Data Mining goals)

### 1.2.1. Планируемый подход (Two-stage Anomaly Detection)
На основе консультации с экспертом выбран двухэтапный подход:
1.  **Этап 1 (Unsupervised):** Обучение модели без учителя (Isolation Forest) для первичного поиска кандидатов в аномалии.
2.  **Этап 2 (Human-in-the-loop):** Ручная валидация найденных аномалий экспертом для формирования размеченного датасета.
3.  **Этап 3 (Supervised):** Обучение модели с учителем (XGBoost) на размеченных данных для повышения точности и снижения ложных срабатываний.
Такой подход позволяет использовать преимущества обоих методов: быстро находить аномалии без разметки на старте и повышать качество модели за счет экспертной обратной связи.

### 1.2.2. Дерево метрик (Metric Tree)
Как бизнес-цель раскладывается на технические метрики:
1.  **Бизнес-цель:** Снизить потери выручки на 5%.
2.  **Бизнес-метрика:** Время обнаружения аномалии < 24 часов.
3.  **ML-метрика:** Recall ≥ 0.8 (найти 80% аномалий).
4.  **Метрика модели:** F1-score ≥ 0.75 (баланс Precision и Recall).

### 1.2.3. Метрики оценки и стоимость ошибок
*   **ML-метрики:**
    *   **Precision** — доля истинных аномалий среди всех, что нашла модель.
    *   **Recall** — доля найденных аномалий среди всех реальных.
    *   **F1-score** — гармоническое среднее Precision и Recall.
*   **Стоимость ошибок:**
    *   **False Positive (ложное срабатывание):** Аналитик тратит 1 час на проверку. Стоимость = 1 час рабочего времени.
    *   **False Negative (пропуск аномалии):** Компания теряет до 100 000 рублей (упущенная выручка, мошенничество).
    *   **Вывод:** Recall важнее Precision. Лучше перестраховаться (больше ложных срабатываний), чем пропустить реальную аномалию.

### 1.2.4. Критерий успешности модели
*   **Минимальный порог:** F1-score ≥ 0.6 (модель должна находить хотя бы 60% аномалий).
*   **Оптимальный:** F1-score ≥ 0.75.

### 1.2.5. Критерии приемки (Acceptance Criteria)
*   Модель должна выдавать алерт в течение **1 часа** после закрытия дня.
*   Сервис должен обрабатывать **1000 запросов в минуту** (для API).
*   Документация (README) должна содержать инструкции по запуску и примеры запросов.
